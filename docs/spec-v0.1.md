# 운동 기록 앱 개발 스펙 v0.1

> 작성일: 2026-08-24
> 상태: 확정 (구현 착수 가능)

---

## 1. 목적과 범위

### 1.1 왜 만드는가

시중 운동 기록 앱으로 해결되지 않는 문제가 두 가지 있다.

1. **주간 리포트 자동화** — 매주 운동 데이터를 정리해 Claude에게 전달하고 다음 주차 계획을 받는 루프가 있다. 현재 이 정리를 수동 타이핑으로 하고 있으며, 그 결과 형식이 뭉개지고 컨디션·수행 세부가 누락된다.
2. **비중량 종목 표현** — 흉추 모빌리티 드릴 같은 종목을 `0 kg × 1`로 우회 입력해야 한다.

이 두 가지가 이 앱의 존재 이유다. 나머지 기능은 기존 앱 수준을 따라가는 것이 목표이며, 능가할 필요가 없다.

### 1.2 사용자

본인 1명. 인증·멀티테넌시·소셜 기능 일체 불필요.

### 1.3 비용 제약

**총 0원.** 유료 전환이 필요한 선택지는 채택하지 않는다.

## 2. 아키텍처 결정

### 2.1 로컬 온리 (서버 없음)

모든 데이터는 기기 내 IndexedDB에 저장한다. 백엔드 서버, 데이터베이스 서버, 인증 없음.

**근거**

- 헬스장은 신호가 불안정하다. 오프라인 동작이 선택이 아니라 필수다.
- WebKit 공식 문서: 홈 화면 웹앱의 first-party 도메인은 ITP의 7일 저장소 삭제 상한에서 **명시적으로 제외**되며, 데이터가 Safari와 격리 보관된다. 주 4회 사용하는 앱에서 로컬 저장소는 충분히 안전하다.
- 데이터량 추정: 주 80세트 → 연 4,000세트 → 연 약 400KB. 용량 한도와 무관.
- 서버가 없으므로 인증, 세션, CORS, 배포 파이프라인 복잡도가 전부 사라진다.

**Phase 2 (선택)** — Spring Boot 동기화 서버를 나중에 추가할 수 있다. 앱이 서버 없이 완전히 동작하므로 무료 티어의 콜드 스타트가 문제되지 않는다. 단 v1 범위 밖.

### 2.2 PWA (네이티브 아님)

**근거**

- 네이티브 iOS는 홈 화면 위젯이 가능하지만 Apple Developer Program 연 $99가 필요하다. 무료 계정은 7일마다 재설치해야 한다.
- PWA는 홈 화면 추가 후 만료가 없다. 0원 제약을 만족하는 유일한 선택.
- 위젯을 포기하는 대가로 얻는 것이 없으므로, 위젯은 범위에서 제외한다.

### 2.3 백업 전략

로컬 온리의 유일한 실질 리스크는 기기 분실·초기화다.

1. **JSON 내보내기/가져오기** — 전체 DB를 파일 하나로. 주간 리포트 생성 시 함께 다운로드되도록 묶는다.
2. **주간 리포트가 이차 백업** — Claude에게 전달하는 마크다운이 해당 주 기록 전체를 포함한다.
3. `navigator.storage.persist()` 호출 — 홈 화면 앱이면 이미 안전하지만 이중 보호는 무비용.

### 3.1 GitHub Pages 주의사항

저장소 이름을 `<username>.github.io`로 만든다. 그러면 앱이 루트 경로에서 서비스되어 Vite `base`, manifest `start_url`/`scope` 설정이 불필요하다. 하위 경로(`/repo-name/`)로 배포하면 서비스워커 등록이 실패하기 쉽다.

데이터가 전부 로컬이므로 **저장소를 공개해도 무방하다.** 방문자에게는 빈 앱이 보일 뿐이다.

## 4. 도메인 모델

### 4.1 exerciseType

3종으로 확정. 신규 종목 생성 시 기본값은 `WEIGHT_REPS`.

| 타입          | 입력 칸  | 볼륨 집계 | 예시                                                     |
| ------------- | -------- | --------- | -------------------------------------------------------- |
| `WEIGHT_REPS` | kg, 렙   | 포함      | 벤치프레스, 스쿼트, 풀업(추가중량), 사이드 레터럴 레이즈 |
| `TIME`        | 초       | 제외      | 플랭크                                                   |
| `CHECKLIST`   | 체크박스 | **제외**  | 흉추 모빌리티 드릴, 활성화 워밍업, 쿨다운                |

`CHECKLIST`를 세트 수 카운트에서도 제외하는 것이 중요하다. 현재 우회 방식(`0kg × 1`)은 주간 총 세트를 부풀린다.

**의도적으로 제외한 타입**

- `BODYWEIGHT_REPS` — 풀업은 kg 칸에 추가 중량(없으면 0)을 넣으면 충분하며, 중량 풀업으로 진행할 예정이므로 `WEIGHT_REPS`가 맞다.
- `DISTANCE_TIME` — 러닝은 웨이트 템플릿의 종목이 아니라 별도 세션으로 다룬다. 기록 항목, 화면, 진척 지표가 전부 다르다.

### 4.2 엔티티

```
Exercise                    종목 마스터
  id, name, type, note, isArchived, createdAt

Template                    "Bench Main" 등
  id, name, sortOrder, isArchived

TemplateExercise            템플릿 안의 종목 + 목표치
  id, templateId, exerciseId, sortOrder,
  targetSets, targetReps, targetWeight, targetSeconds,
  restSeconds, note

Workout                     실제 수행 세션
  id, templateId, templateName,
  startedAt, endedAt,
  sleepHours, backCondition, kneeCondition, conditionScore,
  note

WorkoutExercise
  id, workoutId, exerciseId, exerciseName, sortOrder,
  isChecked                 -- CHECKLIST 타입용

WorkoutSet
  id, workoutExerciseId, exerciseId, setNumber, setType,
  weight, reps, seconds,
  isCompleted, completedAt

Run                         러닝 세션 (별도)
  id, startedAt, durationSec, distanceKm, note, feelScore

Bodyweight
  date, weightKg
```

### 4.3 핵심 설계 원칙: 스냅샷 복사

**세션은 템플릿을 참조하지 않고 복사한다.**

```
템플릿 시작 시:
  TemplateExercise 목록 → WorkoutExercise로 복사
  이후 세션은 템플릿과 완전히 독립

Workout.templateId  = "어느 템플릿에서 시작했는지" 라벨. 조회 시 조인하지 않음
Workout.templateName, WorkoutExercise.exerciseName = 표시용 복사본
```

**근거** — 템플릿에서 종목을 빼거나 이름을 바꿔도 과거 기록이 변형되면 안 된다. 템플릿을 자유롭게 편집할수록 이 분리가 더 중요해진다. 이를 지키지 않으면 점진적 과부하 그래프에 구멍이 생긴다.

이 구조의 부수 효과로 **세션 중 종목·세트 추가/삭제가 자동으로 가능**해진다. 랙이 차 있거나 컨디션이 나쁠 때의 즉석 변경을 지원한다.

### 4.4 슈퍼세트

**데이터 모델에서 표현하지 않는다.** 종목을 순서대로 배치하고 앞 종목의 `restSeconds`를 0으로 두어 갈음한다. 그룹 필드와 번갈아 입력하는 UI를 없애 구현 난이도를 크게 낮춘다.

### 4.5 Dexie 스키마

```javascript
db.version(1).stores({
  exercises: 'id, name, type',
  templates: 'id, sortOrder',
  templateExercises: 'id, templateId, sortOrder',
  workouts: 'id, startedAt',
  workoutExercises: 'id, workoutId, exerciseId, sortOrder',
  workoutSets: 'id, workoutExerciseId, [exerciseId+completedAt]',
  runs: 'id, startedAt',
  bodyweights: 'date',
});
```

복합 인덱스 `[exerciseId+completedAt]`이 앱의 두 핵심 기능을 전담한다.

- "이 종목 최근 기록" 조회 (종목 선택 시 직전 수행값 표시)
- 점진적 과부하 그래프 (날짜별 지표 추이)

IndexedDB는 조인이 없다. 서버 DB처럼 엄격히 정규화하지 말고 표시용 이름은 비정규화한다.

### 5.1 세션 진행 화면 (5번) — 승부처

헬스장에서 땀난 손으로, 세트 사이 짧은 시간에, 한 손으로 조작한다.

- 터치 타겟 최소 44px
- 숫자 입력은 `inputmode="decimal"` (숫자 키패드)
- **이전 세트 값을 기본값으로 미리 채워둔다** — 대부분의 세트는 같은 중량 반복이므로 입력 없이 체크만 하면 되도록
- "이전" 열에 직전 세션의 같은 세트 번호 실제 수행값 표시
- 세트 완료 체크 시 휴식 타이머 자동 시작

## 6. 타이머

### 6.1 총 세션 시간

`startedAt` 타임스탬프만 저장하고 표시 시점에 `Date.now() - startedAt`으로 계산한다. 카운트업 루프를 돌리지 않으므로 백그라운드 전환 후 복귀해도 값이 정확하다.

### 6.2 세트별 휴식 타이머

**iOS PWA는 백그라운드에서 타이머를 이어갈 수 없다.** 해결 우선순위:

**1순위 — Screen Wake Lock API.** Safari 18.4부터 홈 화면 웹앱은 화면 꺼짐·잠금을 막을 수 있다. 세션 시작 시 wake lock 획득, 종료 시 해제. 화면이 켜져 있으면 JS 타이머가 정상 동작하고 소리·진동도 즉시 울린다. 세트 사이에 폰을 보며 쉬는 것은 자연스러운 행동이므로 실사용 영향이 작다.

**2순위 (v1 범위 밖) — 서버 예약 웹푸시.** Apple이 권장하는 방식이지만 iOS에서 푸시 구독이 예고 없이 만료되는 문제가 반복 보고된다. 매 세트 의존하는 기능을 여기에만 걸 수 없다. 서버가 필요하므로 Phase 2 이후.

**채택하지 않음 — 무음 오디오 루프.** iOS에서 불안정하고 배터리 소모가 크다.

Wake Lock은 실기기에서만 검증 가능하다. 데스크톱 브라우저·시뮬레이터로는 확인되지 않는다.

## 7. 점진적 과부하 지표

세 지표를 함께 표시한다. 총 볼륨만 보면 함정이 있다 — 80kg×7을 85kg×5로 바꾸면 볼륨은 줄지만 실제로는 강해진 것이다.

| 지표           | 계산                            | 무엇을 보는가                            |
| -------------- | ------------------------------- | ---------------------------------------- |
| 세션 총 볼륨   | `Σ(weight × reps)`              | 전체 작업량 추세                         |
| **추정 1RM**   | Epley: `weight × (1 + reps/30)` | 중량·렙이 바뀌어도 비교 가능한 절대 근력 |
| 세트 최고 중량 | `max(weight)`                   | 가장 직관적인 심리 지표                  |

**e1RM이 핵심 지표다.** 현재 프로그램은 하체 선형 증량, 상체 이중 progression이라 렙이 계속 변한다. 렙이 바뀌는 구간에서 진척을 판정하려면 단일 축이 필요하다.

`setType`(`WARMUP`/`NORMAL`/`FAILURE`/`DROP`)을 처음부터 넣는다. 워밍업 세트를 본세트와 구분하지 않으면 볼륨 그래프가 오염된다.

## 8. 주간 리포트 (이 앱의 존재 이유)

부가 기능이 아니라 v1의 중심이다. 4주차에 반드시 구현한다.

### 8.1 다섯 항목 (기존 피드백 루프 합의 형식)

| 항목           | 자동화        | 방법                                     |
| -------------- | ------------- | ---------------------------------------- |
| 1. 웨이트 수행 | **완전 자동** | 기록 그 자체                             |
| 2. 러닝        | 부분 자동     | 거리·시간 자동, 체감은 세션 종료 시 입력 |
| 3. 식단        | **불가능**    | 리포트 생성 시 사용자에게 질문           |
| 4. 체중        | 자동          | 매일 아침 입력 → 주 평균 계산            |
| 5. 컨디션      | 자동          | 세션 종료 시 수면·허리·무릎 입력         |

**설계 결정: 세션 종료 화면에서 컨디션 입력을 강제한다.** 주말에 몰아서 기억하면 부정확하다. 운동 직후 슬라이더 3개는 부담이 없다.

리포트 생성 버튼 → 3번만 질문 → 마크다운 생성 → `navigator.clipboard.writeText()`.

### 8.2 출력 형식

```markdown
## 2026-08-17 ~ 08-23 (프로그램 N주차)

**수행**: 웨이트 4/4, 러닝 1/2
**체중**: 시작 74.2kg → 종료 73.8kg (주간 평균 74.0kg)

### 8/18 (화) Bench Main — 62분

| 종목        | 세트별 수행            | 총 볼륨 | e1RM          |
| ----------- | ---------------------- | ------- | ------------- |
| Bench Press | 80×7, 80×7, 80×7, 80×5 | 2,080kg | 98.7kg (+1.2) |
| Barbell Row | 60×8, 60×8, 60×7       | 1,380kg | 75.0kg (+0)   |

- 흉추 모빌리티 드릴 ✓
- 컨디션: 수면 7h / 허리 양호 / 무릎 양호

### 8/20 (목) Squat Main — 71분

...

### 러닝

- 8/22 (토) 5.2km / 34분 / 체감 3

### 식단

- 뷔페 규칙 준수 4/5일
- 이탈: 금요일 회식

### 주간 요약

- 총 볼륨: 18,240kg (전주 대비 +4.2%)
- e1RM 변화: 벤치 +1.2 / 스쿼트 +2.5 / 데드 +0 / OHP -0.8
- 미달성: 러닝 1회
```

**전주 대비 증감을 앱이 미리 계산해 넣는다.** Claude가 두 주치를 받아 비교하는 것보다 정확하다.

이미지가 아니라 텍스트로 출력한다. 파싱 정확도와 용량 모두 유리하다.

## 9. 개발 일정

```
1주차  Vite + React + Dexie 스키마
       종목 CRUD, 템플릿 CRUD
       → 현재 쓰는 앱을 보며 종목 15~20개 직접 입력 (첫 실사용 테스트)

2주차  세션 진행 화면 — 템플릿 시작, 세트 입력, "이전" 열
       ★ 가장 어렵고 가장 중요

3주차  타이머 (Wake Lock + 총 시간 + 휴식)
       vite-plugin-pwa 적용, GitHub Pages 배포
       ★ 헬스장에서 실제 한 세션 수행

4주차  주간 리포트 마크다운 생성 + JSON 백업/복원

5주차  점진적 과부하 그래프, UI 정리
───── 여기까지 0원, 완결 ─────
이후   Spring Boot 동기화 서버 (선택)
```

3주차에 실사용이 시작되는 것이 중요하다. 배포가 `git push` 한 번이므로 서버가 있는 구성보다 앞당겨진다.

**전환은 점진적으로.** 앱 완성 후에도 1~2개월은 기존 앱과 병행 기록하고, 충분히 편해진 뒤 갈아탄다. 앱 개발 때문에 훈련 데이터에 구멍이 생기는 것은 우선순위 역전이다.
