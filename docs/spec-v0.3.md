# 운동 기록 앱 개발 스펙 v0.3

> 최초 작성: 2026-08-24 (v0.1)
> 갱신: 2026-09-14 (v0.3 — 세션 종료 요약, 앱 영역 설정)
> 상태: 1~4주차 구현 완료. 배포·백업·그래프 미착수

---

## 1. 목적과 범위

### 1.1 왜 만드는가

시중 운동 기록 앱으로 해결되지 않는 문제가 두 가지 있다.

1. **주간 리포트 자동화** — 매주 운동 데이터를 정리해 Claude에게 전달하고 다음 주차 계획을 받는 루프가 있다. 현재 이 정리를 수동 타이핑으로 하고 있으며, 그 결과 형식이 뭉개지고 컨디션·수행 세부가 누락된다.
2. **비중량 종목 표현** — 흉추 모빌리티 드릴 같은 종목을 `0 kg × 1`로 우회 입력해야 한다.

이 두 가지가 이 앱의 존재 이유다. 나머지 기능은 기존 앱 수준을 따라가는 것이 목표이며, 능가할 필요가 없다.

### 1.2 사용자

본인 1명. 인증·멀티테넌시·소셜 기능 일체 불필요.

### 1.3 비용 제약

**총 0원.** 유료 전환이 필요한 선택지는 채택하지 않는다.

## 2. 아키텍처 결정

### 2.1 로컬 온리 (서버 없음)

모든 데이터는 기기 내 IndexedDB에 저장한다. 백엔드 서버, 데이터베이스 서버, 인증 없음.

**근거**

- 헬스장은 신호가 불안정하다. 오프라인 동작이 선택이 아니라 필수다.
- WebKit 공식 문서: 홈 화면 웹앱의 first-party 도메인은 ITP의 7일 저장소 삭제 상한에서 **명시적으로 제외**되며, 데이터가 Safari와 격리 보관된다. 주 4회 사용하는 앱에서 로컬 저장소는 충분히 안전하다.
- 데이터량 추정: 주 80세트 → 연 4,000세트 → 연 약 400KB. 용량 한도와 무관.
- 서버가 없으므로 인증, 세션, CORS, 배포 파이프라인 복잡도가 전부 사라진다.

**Phase 2 (선택)** — Spring Boot 동기화 서버를 나중에 추가할 수 있다. 앱이 서버 없이 완전히 동작하므로 무료 티어의 콜드 스타트가 문제되지 않는다. 단 v1 범위 밖.

### 2.2 PWA (네이티브 아님)

**근거**

- 네이티브 iOS는 홈 화면 위젯이 가능하지만 Apple Developer Program 연 $99가 필요하다. 무료 계정은 7일마다 재설치해야 한다.
- PWA는 홈 화면 추가 후 만료가 없다. 0원 제약을 만족하는 유일한 선택.
- 위젯을 포기하는 대가로 얻는 것이 없으므로, 위젯은 범위에서 제외한다.

### 2.3 백업 전략

로컬 온리의 유일한 실질 리스크는 기기 분실·초기화다.

1. **JSON 내보내기/가져오기** — 전체 DB를 파일 하나로. 주간 리포트 생성 시 함께 다운로드되도록 묶는다. **(미구현 — §11)**
2. **주간 리포트가 이차 백업** — Claude에게 전달하는 마크다운이 해당 주 기록 전체를 포함한다. **(구현됨)**
3. `navigator.storage.persist()` 호출 — 홈 화면 앱이면 이미 안전하지만 이중 보호는 무비용. **(구현됨 — 앱 시작 시 1회)**

### 3.1 GitHub Pages 주의사항

저장소 이름을 `<username>.github.io`로 만든다. 그러면 앱이 루트 경로에서 서비스되어 Vite `base`, manifest `start_url`/`scope` 설정이 불필요하다. 하위 경로(`/repo-name/`)로 배포하면 서비스워커 등록이 실패하기 쉽다.

데이터가 전부 로컬이므로 **저장소를 공개해도 무방하다.** 방문자에게는 빈 앱이 보일 뿐이다.

### 3.2 해시 라우팅 (v0.2 추가)

`HashRouter`를 쓴다. GitHub Pages에는 SPA 폴백이 없어 `/templates/abc`를 새로고침하면 404가 난다. 404.html 트릭 대신 해시를 쓰면 서비스워커 등록(§3.1)과도 부딪히지 않고, iOS 스탠드얼론 PWA의 스와이프 뒤로가기도 정상 동작한다.

라우트: `/`(홈) · `/workouts/:id` · `/exercises` · `/templates` · `/templates/:id` · `/report`

## 4. 도메인 모델

### 4.1 exerciseType

3종으로 확정. 신규 종목 생성 시 기본값은 `WEIGHT_REPS`.

| 타입          | 입력 칸  | 볼륨 집계 | 예시                                                     |
| ------------- | -------- | --------- | -------------------------------------------------------- |
| `WEIGHT_REPS` | kg, 렙   | 포함      | 벤치프레스, 스쿼트, 풀업(추가중량), 사이드 레터럴 레이즈 |
| `TIME`        | 초       | 제외      | 플랭크                                                   |
| `CHECKLIST`   | 체크박스 | **제외**  | 흉추 모빌리티 드릴, 활성화 워밍업, 쿨다운                |

`CHECKLIST`를 세트 수 카운트에서도 제외하는 것이 중요하다. 현재 우회 방식(`0kg × 1`)은 주간 총 세트를 부풀린다.

**타입이 결정하는 것 (v0.2 명시)**

- 템플릿 편집의 목표치 입력 칸: `WEIGHT_REPS` → 세트/렙/중량/휴식, `TIME` → 세트/시간/휴식, `CHECKLIST` → 목표치 없음
- 세션 진행의 세트 행: `WEIGHT_REPS` → kg·회, `TIME` → 초, `CHECKLIST` → 세트 없이 체크 하나
- 주간 리포트: `CHECKLIST`는 표가 아니라 체크 목록으로

**의도적으로 제외한 타입**

- `BODYWEIGHT_REPS` — 풀업은 kg 칸에 추가 중량(없으면 0)을 넣으면 충분하며, 중량 풀업으로 진행할 예정이므로 `WEIGHT_REPS`가 맞다.
- `DISTANCE_TIME` — 러닝은 웨이트 템플릿의 종목이 아니라 별도 세션으로 다룬다. 기록 항목, 화면, 진척 지표가 전부 다르다.

### 4.2 엔티티

```
Exercise                    종목 마스터
  id, name, type, note, isArchived, createdAt

Template                    "Bench Main" 등
  id, name, sortOrder, isArchived

TemplateExercise            템플릿 안의 종목 + 목표치
  id, templateId, exerciseId, sortOrder,
  targetSets, targetReps, targetWeight, targetSeconds,
  restSeconds, note

Workout                     실제 수행 세션
  id, templateId, templateName,
  startedAt, endedAt,
  sleepHours, backCondition, kneeCondition, conditionScore,
  note

WorkoutExercise
  id, workoutId, exerciseId, exerciseName, exerciseType,
  sortOrder, restSeconds, isChecked

WorkoutSet
  id, workoutExerciseId, exerciseId, setNumber, setType,
  weight, reps, seconds,
  isCompleted, completedAt

Run                         러닝 세션 (별도)
  id, startedAt, durationSec, distanceKm, note, feelScore

Bodyweight
  date, weightKg
```

**v0.2에서 추가한 필드**

| 필드                          | 이유                                                                                                                                   |
| ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| `WorkoutExercise.exerciseType` | 어떤 입력 칸을 그릴지가 타입으로 정해진다. 조인해서 읽으면 나중에 종목 타입을 바꾸거나 종목을 삭제했을 때 과거 기록을 그리지 못한다.    |
| `WorkoutExercise.restSeconds`  | 휴식 타이머(§6.2)의 길이. 진행 중에 템플릿을 고쳐도 이번 세션의 휴식이 바뀌면 안 되고, 세션 중 즉석 추가한 종목은 참조할 템플릿 행이 없다. |

둘 다 §4.3의 스냅샷 복사 원칙을 그대로 따른 것이다. 이름을 복사하는 이유와 같다.

**타임스탬프 규칙 (v0.2 확정)**

모든 시각은 **epoch ms(number)**다. §6.1이 `Date.now() - startedAt`으로 계산하라고 명시하고, §2.3의 JSON 백업에서 `Date` 객체는 직렬화 왕복이 지저분해진다. 복합 인덱스 `[exerciseId+completedAt]`도 number에서 정상 동작한다.

예외는 `Bodyweight.date`로, 하루 한 건이므로 `'yyyy-MM-dd'` 문자열을 기본키로 쓴다.

**미사용 필드**

`Workout.conditionScore`는 정의만 있고 입력받지 않는다. §8.1이 "수면·허리·무릎" 3개, "슬라이더 3개"로 못박아서 네 번째 입력을 임의로 만들지 않았다. 나중에 파생 계산에 쓰거나 입력을 추가할 여지로 남긴다.

### 4.3 핵심 설계 원칙: 스냅샷 복사

**세션은 템플릿을 참조하지 않고 복사한다.**

```
템플릿 시작 시:
  TemplateExercise 목록 → WorkoutExercise로 복사
  이후 세션은 템플릿과 완전히 독립

Workout.templateId  = "어느 템플릿에서 시작했는지" 라벨. 조회 시 조인하지 않음
Workout.templateName, WorkoutExercise.exerciseName/exerciseType/restSeconds
                    = 표시·진행용 복사본
```

**근거** — 템플릿에서 종목을 빼거나 이름을 바꿔도 과거 기록이 변형되면 안 된다. 템플릿을 자유롭게 편집할수록 이 분리가 더 중요해진다. 이를 지키지 않으면 점진적 과부하 그래프에 구멍이 생긴다.

이 구조의 부수 효과로 **세션 중 종목·세트 추가/삭제가 자동으로 가능**해진다. 랙이 차 있거나 컨디션이 나쁠 때의 즉석 변경을 지원한다.

#### 4.3.1 복사하지 않는 것 (v0.2 명시)

**템플릿은 종목을 참조한다. 복사하지 않는다.**

스냅샷 원칙은 **Workout에만** 적용된다. `TemplateExercise.exerciseId`는 살아 있는 참조이고, 템플릿 편집 화면의 종목 이름은 표시 시점에 `bulkGet`으로 붙인다. 종목 이름을 고치면 템플릿에 즉시 반영되는 것이 맞다 — 그건 원칙이 막으려던 문제가 아니다. 템플릿이 옛 이름을 붙들고 있으면 오히려 버그다.

#### 4.3.2 세션 시작 시 세트 값의 출처 (v0.2 추가)

세트는 미리 만들어 두고 값을 채워 둔다(§5.1 "미리 채워둔다"). 출처는 두 가지다.

1. **직전 세션** — 같은 템플릿의 가장 최근 종료 세션에서 **완료 체크된 세트**를 세트 수·중량·렙·`setType`까지 그대로 가져온다. 매주 다시 입력할 필요가 없고, 워밍업 세팅도 따라온다.
2. **템플릿 목표치** — 직전 세션이 없거나 완료한 세트가 없으면 `targetSets`/`targetReps`/`targetWeight`/`targetSeconds`.

완료 체크가 없던 세트는 수행하지 않은 것이므로 가져오지 않는다. 그러지 않으면 안 한 세트가 매주 불어난다.

**부작용** — 직전 세션 값이 템플릿 목표치를 덮는다. 템플릿에서 목표 중량을 고쳐도 직전에 다른 중량으로 했으면 그 값이 들어온다. 템플릿 목표치는 사실상 그 종목의 첫 세션에서만 쓰인다. "매주 다시 입력하지 않는다"를 우선한 결과다.

### 4.4 슈퍼세트

**데이터 모델에서 표현하지 않는다.** 종목을 순서대로 배치하고 앞 종목의 `restSeconds`를 0으로 두어 갈음한다. 그룹 필드와 번갈아 입력하는 UI를 없애 구현 난이도를 크게 낮춘다.

`restSeconds`가 0이면 휴식 타이머를 걸지 않는다(§6.2). 쉬지 않고 다음 종목으로 넘어가는 것이 슈퍼세트의 의도이기 때문이다.

### 4.5 Dexie 스키마

```javascript
db.version(1).stores({
  exercises: 'id, name, type',
  templates: 'id, sortOrder',
  templateExercises: 'id, templateId, sortOrder',
  workouts: 'id, startedAt',
  workoutExercises: 'id, workoutId, exerciseId, sortOrder',
  workoutSets: 'id, workoutExerciseId, [exerciseId+completedAt]',
  runs: 'id, startedAt',
  bodyweights: 'date',
})
```

복합 인덱스 `[exerciseId+completedAt]`이 앱의 두 핵심 기능을 전담한다.

- "이 종목 최근 기록" 조회 → 주간 리포트의 e1RM 증감 괄호가 이걸 쓴다
- 점진적 과부하 그래프 (5주차)

IndexedDB는 조인이 없다. 서버 DB처럼 엄격히 정규화하지 말고 표시용 이름은 비정규화한다.

**8개를 한 번에 선언한 이유 (v0.2)** — 1주차에 실제로 쓴 스토어는 3개뿐이지만, 나머지를 나중에 추가하면 `version(2)` 마이그레이션이 생긴다. 실사용 데이터가 들어간 뒤 스키마를 올리는 것보다 빈 DB일 때 전부 선언하는 쪽이 안전하다.

**인덱스에 없는 필드는 메모리에서 거른다.** `isArchived`, `templateExercises.exerciseId` 등이 그렇다. 종목 15~20개, 템플릿 4개 규모라 전체 스캔이 인덱스보다 싸다.

**완료 체크를 풀면 `completedAt`을 반드시 지운다.** 안 지우면 `[exerciseId+completedAt]` 인덱스에 유령이 남아 "최근 기록"이 틀린 값을 보게 된다.

| 10  | 설정          | ✗    | 데이터 내보내기/가져오기 — **미구현(§11)**           |

설정 탭이 없으므로 주간 리포트 진입점은 홈의 "기록" 헤더 옆에 둔다. 하단 탭은 홈 / 종목 / 템플릿 3개다.

### 5.0 앱 영역 설정 (v0.3 추가)

운동 기록과 가계부는 DB부터 분리된 별개의 앱이다. **둘 중 하나만 쓸 수 있어야 한다.**

- `/settings`에서 각 영역을 켜고 끈다. 진입점은 좌측 상단 전환 토글 옆의 설정 버튼이다
- 끈 영역은 화면과 전환 토글에서 사라지고, 그 경로로 들어오면 켜진 쪽으로 보낸다
- **데이터는 지우지 않는다.** 다시 켜면 그대로 돌아온다
- **마지막 하나는 끌 수 없다.** 둘 다 끄면 남는 화면이 없다

설정은 `workout-log`의 `appSettings` 스토어에 둔다(`version(2)`). 값 자체는 영역
중립이지만 어딘가에는 있어야 하고, localStorage는 규약상 쓰지 않는다.

### 5.1 세션 진행 화면 (5번) — 승부처

헬스장에서 땀난 손으로, 세트 사이 짧은 시간에, 한 손으로 조작한다.

- 터치 타겟 최소 44px
- 숫자 입력은 `inputmode="decimal"` (숫자 키패드). `type="number"` 대신 `type="text"` + `inputMode`를 쓴다 — iOS에서 `"82."` 같은 입력 중간 상태가 통째로 버려지는 것을 피하기 위해서다.
- **세트 값을 기본값으로 미리 채워둔다** — 출처는 §4.3.2
- 세트 완료 체크 시 휴식 타이머 자동 시작 (§6.2)
- **세트 번호를 탭하면 `setType`이 본세트 → 워밍업 → 실패 → 드롭으로 순환한다.** §7이 워밍업 구분을 요구하는데 세션 중에 바꿀 수단이 없으면 그 필드가 죽는다.
- 세트 삭제는 "− 마지막 세트" 버튼. 행마다 × 를 넣으면 완료 체크 옆에 파괴적 버튼이 붙어 오조작 위험이 크고, 실제로 필요한 건 대개 마지막 세트를 빼는 경우다.
- 헤더에 [운동 취소] / [운동 종료]. 취소가 좁고 종료가 넓다.

**"이전" 열은 아직 없다.** §4.3.2의 직전 세션 복사가 "같은 중량 반복"은 해결하지만, 직전 세션의 실제 수행값을 나란히 보여주는 열은 미구현이다(§11).

### 5.1.1 세션 종료 요약 (v0.3 추가)

종료 시트에서 두 가지를 더 보여준다.

**직전 세션 대비 중량 증감** — 종목별 최고 중량과 그 변화(`+5kg` / `-2.5kg`).
§7의 세 지표 중 "가장 직관적인 심리 지표"가 최고 중량이고, 세션을 끝낸 직후가
그걸 확인하기 가장 좋은 시점이다. 워밍업·미완료 세트는 제외한다(§7.1).

**템플릿 갱신 제안** — 이번에 한 값이 템플릿 목표치와 다르면 항목별 체크박스로
반영 여부를 묻는다.

세션은 스냅샷이라 템플릿과 독립이고(§4.3), 다음 세션은 직전 세션 값을
복사하므로(§4.3.2) 템플릿을 고치지 않아도 동작은 이어진다. 다만 **템플릿 편집
화면에 옛 목표치가 남아 혼란스럽다.** 그래서 제안하되 강제하지 않는다.

- 비교 대상은 세트 수 · 렙 · 중량
- 실제 값은 완료한 본세트의 **최빈값**을 쓴다. 동률이면 큰 쪽 — 증량한 세트가 기준이 된다
- 과거 기록은 건드리지 않는다. 바뀌는 것은 템플릿의 목표치뿐이다

### 5.2 템플릿 편집의 저장 정책 (v0.2 추가)

**모든 변경은 로컬 드래프트에 쌓이고 [저장]을 눌러야 DB에 커밋된다.** 이름·종목 추가/삭제/순서/목표치가 전부 해당된다.

**근거** — 종목을 추가하자마자 저장되면 "아직 편집 중"과 "반영됨"을 구분할 수 없어 되돌리기가 불가능하다. 저장하지 않고 나가려 하면 확인을 받는다.

**커밋 방식** — 해당 템플릿의 `templateExercises`를 전부 지우고 다시 넣는다. diff보다 단순하고, 이 id를 참조하는 곳이 없어서(세션은 스냅샷 복사다) 재발급해도 안전하다.

### 5.3 삭제 정책 (v0.2 추가)

**아카이브가 기본, 하드 삭제는 확인 후.**

- 종목 하드 삭제 시 참조하는 `templateExercises`까지 한 트랜잭션에서 정리하고, 확인 다이얼로그에 "템플릿 N개에서 함께 제거됩니다 / 과거 운동 기록은 그대로 유지됩니다"를 보여준다.
- 템플릿 하드 삭제 시 안의 종목 구성이 함께 사라진다.
- 세션 기록 삭제는 홈 목록과 세션 상세 양쪽에서 가능하다.

과거 기록이 어느 쪽이든 안전한 이유가 §4.3의 스냅샷 복사다.

## 6. 타이머

### 6.1 총 세션 시간

`startedAt` 타임스탬프만 저장하고 표시 시점에 `Date.now() - startedAt`으로 계산한다. 카운트업 루프를 돌리지 않으므로 백그라운드 전환 후 복귀해도 값이 정확하다.

**구현** — `useElapsed(startedAt)`. 1초 인터벌은 화면을 다시 그리는 신호일 뿐이고, 값은 매 틱마다 차이를 새로 구한다. `visibilitychange`에서 다음 틱을 기다리지 않고 즉시 맞춘다.

### 6.2 세트별 휴식 타이머

**iOS PWA는 백그라운드에서 타이머를 이어갈 수 없다.** 해결 우선순위:

**1순위 — Screen Wake Lock API.** Safari 18.4부터 홈 화면 웹앱은 화면 꺼짐·잠금을 막을 수 있다. 세션 시작 시 wake lock 획득, 종료 시 해제. 화면이 켜져 있으면 JS 타이머가 정상 동작하고 소리·진동도 즉시 울린다. 세트 사이에 폰을 보며 쉬는 것은 자연스러운 행동이므로 실사용 영향이 작다.

**2순위 (v1 범위 밖) — 서버 예약 웹푸시.** Apple이 권장하는 방식이지만 iOS에서 푸시 구독이 예고 없이 만료되는 문제가 반복 보고된다. 매 세트 의존하는 기능을 여기에만 걸 수 없다. 서버가 필요하므로 Phase 2 이후.

**채택하지 않음 — 무음 오디오 루프.** iOS에서 불안정하고 배터리 소모가 크다.

#### 6.2.1 구현 (v0.2)

- 세트 완료 체크 → 그 종목의 `restSeconds`만큼 카운트다운. `restSeconds`가 0(슈퍼세트)이거나 없으면 걸지 않는다.
- `useCountdown(startedAt, endsAt, onFinish)` — §6.1과 같은 방식으로 매 틱 차이를 새로 구한다. 틱은 250ms다. 표시는 초 단위지만 종료 시점을 1초 안에 잡아야 알람이 늦지 않는다.
- 시작 시각을 함께 넘기는 이유는 렌더를 순수하게 유지하기 위해서다. 새 타이머의 첫 프레임 기준을 `startedAt`으로 맞추면 렌더 중 `Date.now()`를 부르지 않아도 된다. 연장(+30초)은 `startedAt`을 두고 `endsAt`만 늘리므로 이미 흐른 시간이 보존된다.
- 알람은 **WebAudio 오실레이터 비프(880Hz × 3) + 진동**. 오디오 파일을 쓰지 않아 번들이 늘지 않는다.
- **iOS는 사용자 제스처 없이 시작한 오디오를 막는다.** 세트 완료 탭이 그 제스처이므로 그 순간 `AudioContext`를 열어 두고, 타이머 종료 시 재생한다.
- 세션 중 즉석 추가한 종목은 참조할 템플릿 행이 없어 기본 휴식 120초를 준다(템플릿 추가와 같은 값).

#### 6.2.2 알려진 한계

**무음 모드 아이폰에서는 알림이 전혀 없다.** iOS는 무음 스위치가 켜져 있으면 WebAudio 소리를 내지 않고, iOS Safari에는 Vibration API가 없어 진동으로 대체되지도 않는다. §6.2의 2순위(웹푸시, Phase 2)로만 넘을 수 있다.

Wake Lock은 실기기에서만 검증 가능하다. 데스크톱 브라우저·시뮬레이터로는 확인되지 않는다.

## 7. 점진적 과부하 지표

세 지표를 함께 표시한다. 총 볼륨만 보면 함정이 있다 — 80kg×7을 85kg×5로 바꾸면 볼륨은 줄지만 실제로는 강해진 것이다.

| 지표           | 계산                            | 무엇을 보는가                            |
| -------------- | ------------------------------- | ---------------------------------------- |
| 세션 총 볼륨   | `Σ(weight × reps)`              | 전체 작업량 추세                         |
| **추정 1RM**   | Epley: `weight × (1 + reps/30)` | 중량·렙이 바뀌어도 비교 가능한 절대 근력 |
| 세트 최고 중량 | `max(weight)`                   | 가장 직관적인 심리 지표                  |

**e1RM이 핵심 지표다.** 현재 프로그램은 하체 선형 증량, 상체 이중 progression이라 렙이 계속 변한다. 렙이 바뀌는 구간에서 진척을 판정하려면 단일 축이 필요하다.

`setType`(`WARMUP`/`NORMAL`/`FAILURE`/`DROP`)을 처음부터 넣는다. 워밍업 세트를 본세트와 구분하지 않으면 볼륨 그래프가 오염된다.

### 7.1 집계 규칙 (v0.2 명시)

**집계 대상은 `isCompleted && setType !== 'WARMUP'` 인 세트뿐이다.** 완료 체크가 없는 세트는 수행하지 않은 것이고, 워밍업은 본세트와 섞이면 안 된다. 이 판정은 `isCountedSet()` 한 곳에 모아 볼륨·e1RM·리포트가 같은 규칙을 쓰게 한다.

### 7.2 종목별 소요 시간 (v0.2 추가)

**앞 종목이 끝난 시점부터 이 종목이 끝난 시점까지.** 첫 종목은 세션 시작이 기준이다.

`WorkoutExercise`에 시간 필드를 새로 넣는 대신 세트의 `completedAt`으로 계산한다. 세팅 시간이 포함되므로 "이 종목에 쓴 시간"에 가깝다.

**한계** — 종목을 순서대로 수행한다는 전제가 깔려 있다. 종목 사이를 왔다갔다 하면 값이 흐려진다. 완료한 세트가 없는 종목은 값이 없다.

## 8. 주간 리포트 (이 앱의 존재 이유)

부가 기능이 아니라 v1의 중심이다.

### 8.1 다섯 항목 (기존 피드백 루프 합의 형식)

| 항목           | 자동화        | 방법                                     | 상태 |
| -------------- | ------------- | ---------------------------------------- | ---- |
| 1. 웨이트 수행 | **완전 자동** | 기록 그 자체                             | ✓    |
| 2. 러닝        | 부분 자동     | 거리·시간 자동, 체감은 세션 종료 시 입력 | 렌더만 |
| 3. 식단        | **불가능**    | 리포트 생성 시 사용자에게 질문           | 제외 |
| 4. 체중        | 자동          | 매일 아침 입력 → 주 평균 계산            | 렌더만 |
| 5. 컨디션      | 자동          | 세션 종료 시 수면·허리·무릎 입력         | ✓    |

**설계 결정: 세션 종료 화면에서 컨디션 입력을 강제한다.** 주말에 몰아서 기억하면 부정확하다. 운동 직후 슬라이더 3개는 부담이 없다.

**v0.2 변경 — 식단 질문을 넣지 않는다.** 앱이 모르는 정보를 리포트 생성 시 되묻는 흐름은 만들지 않았다. 필요하면 Claude에게 붙여 넣을 때 직접 덧붙인다.

**러닝·체중은 렌더링만 완성됐다.** 입력 화면(§5의 7번, 10번)이 없어 실제로는 빈 섹션이다. 테이블에 값이 들어가면 바로 출력된다.

### 8.2 출력 형식

```markdown
## 2026-09-07 ~ 09-13

**수행**: 웨이트 1/2
**체중**: 74.2 → 73.8kg (주 평균 74, 전주 74.5)

### 9/8 (화) Bench Main — 62분

| 종목 | 세트별 수행 | 볼륨 | e1RM |
|---|---|---|---|
| 벤치프레스 | 82.5×7, 82.5×7, — | 1,155kg | 101.8 (+3.1) |
| 플랭크 | 60초, — | — | — |

- 흉추 모빌리티 드릴 ✓
- 컨디션: 수면 7h / 허리 4 / 무릎 5

### 러닝

- 9/12 (토) 5.2km / 34분 / 체감 3

### 주간 요약

- 총 볼륨 1,155kg (전주 +3.1%)
- e1RM: 벤치프레스 +3.1
- 미달성: 웨이트 1회
```

**전주 대비 증감을 앱이 미리 계산해 넣는다.** Claude가 두 주치를 받아 비교하는 것보다 정확하다.

이미지가 아니라 텍스트로 출력한다. 파싱 정확도와 용량 모두 유리하다. 화면에도 렌더링하지 않고 마크다운 원문 그대로 미리보기한다 — 예쁘게 렌더링하면 실제로 붙여 넣을 텍스트와 달라져 형식이 뭉개졌는지 확인할 방법이 없어진다.

### 8.3 형식 규칙 (v0.2 확정)

- 기간은 **월~일**. 이전/다음 주 이동 가능. 해당 기간에 **종료된**(`endedAt` 있는) 세션만 집계한다.
- 워밍업 세트는 상세에서 빼고 집계에서도 제외한다(§7.1).
- **미완료 세트는 `—`로 표시한다.** 몇 세트를 못 채웠는지가 보여야 한다.
- e1RM은 세션 내 최고값. 괄호 안은 **같은 종목의 직전 세션 대비** 증감이며, 주 경계를 넘어갈 수 있다. 전주 데이터가 없으면 괄호를 생략한다.
- `CHECKLIST`는 표가 아니라 아래 체크 목록으로(`✓` / `✗`).
- 러닝·체중 데이터가 없으면 해당 섹션과 `**수행**`의 러닝 부분을 생략한다.
- 세션 메모(`Workout.note`)는 리포트에 넣지 않는다.

### 8.4 목표치 문제 (v0.2 — 미해결)

§8.2 원안의 `웨이트 4/4, 러닝 1/2`에서 **분모(주간 목표)를 저장할 곳이 앱에 없다.**

현재 처리:

- **웨이트 분모 = 활성 템플릿 개수.** 템플릿 하나를 주 1회씩 도는 프로그램을 전제한다. 템플릿을 5개 만들어두고 주 4회만 돌면 분모가 5로 잡힌다.
- **러닝은 분모 없이 횟수만.** 근거로 삼을 값이 전혀 없다.
- **"미달성"은 웨이트만 계산한다.**

제대로 하려면 목표 저장소(테이블 또는 설정)가 필요하다. §11에 남긴다.

## 9. 개발 일정

```
1주차  Vite + React + Dexie 스키마                          ✓ 완료
       종목 CRUD, 템플릿 CRUD

2주차  세션 진행 화면 — 템플릿 시작, 세트 입력              ✓ 완료 ("이전" 열 제외)
       ★ 가장 어렵고 가장 중요

3주차  타이머 (Wake Lock + 총 시간 + 휴식)                  ✓ 완료
       vite-plugin-pwa 적용, GitHub Pages 배포             ✗ 미착수
       ★ 헬스장에서 실제 한 세션 수행                       ✗ 미실시

4주차  주간 리포트 마크다운 생성                            ✓ 완료
       JSON 백업/복원                                       ✗ 미착수

5주차  점진적 과부하 그래프, UI 정리                        ✗ 미착수
───── 여기까지 0원, 완결 ─────
이후   Spring Boot 동기화 서버 (선택)
```

3주차에 실사용이 시작되는 것이 중요하다. 배포가 `git push` 한 번이므로 서버가 있는 구성보다 앞당겨진다.

**배포가 밀린 것이 현재 가장 큰 리스크다.** 실기기 검증이 필요한 항목(Wake Lock, 무음 모드 알람, 클립보드 복사, 터치 조작감)이 전부 배포 이후로 미뤄져 있다.

**전환은 점진적으로.** 앱 완성 후에도 1~2개월은 기존 앱과 병행 기록하고, 충분히 편해진 뒤 갈아탄다. 앱 개발 때문에 훈련 데이터에 구멍이 생기는 것은 우선순위 역전이다.

## 10. v1 범위 제외

- 홈 화면 위젯 (PWA 불가)
- 백엔드 서버, 인증, 동기화
- 슈퍼세트 데이터 표현
- 반복 일정, 알림

- 러닝 GPS 추적 (거리·시간 수동 입력)

- 종료된 세션의 수정 — 세션 상세는 읽기 전용이다. 끝난 기록을 고칠 수 있게 하면 "그날 실제로 뭘 했는지"가 흔들린다.
- 리포트 생성 시 식단 질문 (§8.1)
