**v0.9에서 바뀐 것** — 거래 입력의 카테고리 선택을 그룹 시트로 바꿨다(§5.2.2).

**v0.2에서 한 일** — v0.1은 이 프로젝트를 전제하고 쓰였지만, 실제로 얹으려면 빠진 결정이 있었다.
라우팅·탭 설계(§1.5), Dexie 스키마 선언(§3.1), 고정비 중복 방지에 필요한 `fixedCostId`(§3.2),

## 0. 작업 전 확인사항

**기존 운동 기록 기능은 수정하지 않는다.** 가계부는 `src/finance/` 아래 독립 모듈로 추가한다.
단 §1.5의 라우팅 셸은 예외이며, 그 범위는 §1.6에 못박는다.

### 0.1 기존 코드베이스의 실제 컨벤션

```
src/
  db/          Dexie 정의와 쿼리. 컴포넌트는 여기 함수만 호출한다
  lib/         순수 함수와 커스텀 훅 (React 의존 여부로 파일을 나눈다)
  components/  화면에 종속되지 않는 공용 UI
  screens/     라우트 단위 화면
```

가계부는 이 구조를 그대로 복제한다.

```
src/finance/
  db/          finance-log 정의와 쿼리
  lib/         사이클 유틸, 저축률·대출 계산, loanPolicy.ts
  components/  가계부 전용 UI
  screens/     가계부 화면
```

### 0.4 화면 문구는 데이터에 기대지 않는다 (v0.7)

**시드 데이터의 특정 항목을 전제한 설명을 화면에 쓰지 않는다.**

v0.6까지 시뮬레이터와 목표 상세에 특정 자산을 지목한 안내가 박혀 있었다
("○○는 부분만 회수되는데 전액으로 잡혀 있으니…"). 이런 문구는

- 시드 데이터를 아는 사람에게만 읽히고
- 자산 구성을 바꾸면 화면에 남은 채 **틀린 설명**이 되며
- 같은 앱을 다른 자산 구성으로 쓰면 곧바로 어긋난다

대신 **데이터에서 파생된 표현**을 쓴다.

| 쓰지 않는다 | 쓴다 |
|---|---|
| 보증금·청약·현금 (수익률 없음) | 그 외 자산 (수익률 없음) |
| 연금 등 N원은 뺄 수 없어 제외 | 현금화 불가로 표시한 자산 N원은 제외 |
| 전세대출처럼 원금 상환이 0인 부채 | 월 원금 상환이 0인 부채 |

계산의 한계를 알리는 고지는 남긴다 — 잘못 읽으면 재무 판단이 틀어지기 때문이다.
다만 **어떤 자산을 가졌는지 가정하지 않는 문장**으로 쓴다. 대출 정책의
"실제 대출 가능 여부는 금융기관 확인 필요"(§5.5)는 범용 고지이므로 그대로 둔다.

입력 `placeholder`의 예시도 마찬가지다. 특정 상품명 대신 일반적인 이름을 쓴다.

### 0.2 지켜야 할 규칙

| 규칙 | 근거 |
|---|---|
| **named export만.** default export 금지 | 기존 전 파일이 그렇다 |
| **함수형 컴포넌트만** | 〃 |
| **TypeScript strict** | `tsconfig.app.json`에 켜져 있다 |
| **Dexie 쿼리는 `db/` 아래에만.** 컴포넌트가 `db`를 직접 import하지 않는다 | 〃 |
| **React에 의존하지 않는 순수 함수는 훅과 파일을 분리한다** | `lib/duration.ts`(순수)와 `lib/useElapsed.ts`(훅)가 그 예다. 섞으면 Node에서 계산 로직만 돌려볼 수 없다 |
| **터치 타겟 최소 44px** | 운동 쪽 UI 규약 |
| **금액·날짜 입력은 `type="text"` + `inputMode`** | `type="number"`는 iOS에서 입력 중간 상태를 버린다 |
| localStorage / sessionStorage 사용 금지 | 용량·트랜잭션·인덱스 모두 IndexedDB가 낫다 |

### 0.3 재사용할 공통 컴포넌트 (`src/components/`)

실제로 있는 것과 그 시그니처다.

| 컴포넌트 | 비고 |
|---|---|
| `Button` | `variant: 'primary' \| 'secondary' \| 'ghost' \| 'danger'`, `min-h-11` |
| `IconButton` | 44px 정사각 |
| `Sheet` | 바텀 시트. `{ title, onClose, children, footer }` |
| `ConfirmDialog` | `{ title, description, confirmLabel?, onConfirm, onCancel }` |
| `EmptyState` | `{ title, hint?, action? }` |
| `fields.tsx` | `TextField` · `TextArea` · `NumberField` · `Label` |
| `ArrowIcon` | 순서 이동 버튼용 |
| `MonthCalendar` | 운동 기록 전용 결합이 있다. 가계부에 쓰려면 별도로 만든다 |

**`NumberField`에 천단위 콤마 기능은 없다.** `decimal` prop으로 `inputMode`만 고르고
(`false` → `numeric`, `true` → `decimal`), 표시 포맷은 하지 않는다.
§5.2가 요구하는 콤마 자동 입력은 가계부 전용 `AmountField`를 `src/finance/components/`에 새로 만든다.
공용 `NumberField`를 고치면 운동 쪽 세트 입력에 영향이 간다.

## 1. 아키텍처 결정

### 1.1 Dexie DB를 분리한다

운동 기록은 `workout-log`, 가계부는 **`finance-log`** 라는 별도 데이터베이스를 쓴다.

같은 오리진이라도 데이터베이스 이름이 다르면 완전히 독립적으로 동작한다. 그래서

- 백업 파일을 따로 만들 수 있다
- 한쪽 스키마 버전을 올려도 다른 쪽이 영향받지 않는다
- 한쪽을 통째로 지워도 다른 쪽이 남는다

### 1.2 스키마 버전 관리

`schemaVersion` 필드를 데이터에 넣지 않는다. Dexie가 `db.version(n).stores({...})`로 버전과 마이그레이션을 자체 관리한다.

**스토어는 처음부터 전부 선언한다.** 운동 쪽에서 얻은 교훈이다(`spec-v0.3.md` §4.5) — 실사용 데이터가 들어간 뒤 스토어를 추가하면 마이그레이션을 써야 하지만, 빈 DB일 때 전부 선언하면 그럴 일이 없다.

### 1.3 서버 없음

GitHub Pages 정적 배포이므로 백엔드를 전제한 설계를 하지 않는다. 외부 금융 API 연동(계좌 스크래핑 등)은 정적 사이트에서 불가능하고 보안상으로도 부적절하므로 범위 밖이다.

### 1.4 백업 우선순위

JSON export/import를 **구현 순서 2단계**에 배치한다(원안은 8단계). 시드 데이터 40여 건을 입력한 직후가 유실 시 손실이 가장 큰 시점이다.

```json
{
  "format": "finance-backup",
  "version": 1,
  "exportedAt": 1756000000000,
  "dbVersion": 1,
  "tables": { "transactions": [...], "categories": [...] }
}
```

`tables` 안의 객체는 IndexedDB에 저장된 그대로여야 한다. 복원은 `bulkPut` 한 번으로 끝나고 필드를 추가해도 코드를 고칠 필요가 없다.

**v0.2 정정 — 운동 쪽 백업은 아직 구현되지 않았다.** v0.1은 "운동 쪽 백업과 동일한 구조를 따르되"라고 썼지만 따를 대상이 없다(`spec-v0.3.md` §11). 순서가 뒤집혔으므로 **이 형식이 먼저 확정되고, 나중에 운동 쪽이 `workout-backup`으로 같은 구조를 따른다.**

`format` 필드로 두 백업을 구분하므로, 복원 시 `format`이 `finance-backup`이 아니면 거부한다. 운동 백업 파일을 가계부에 잘못 넣는 사고를 막는다.

### 1.5 라우팅과 내비게이션 (v0.2 추가)

v0.1에 이 결정이 없었다. 없으면 화면을 붙일 수 없다.

**모든 가계부 라우트는 `/finance` 아래에 둔다.**

```
/finance                 대시보드
/finance/new             거래 입력
/finance/report          사이클 리포트
/finance/assets          자산 현황
/finance/goal            목표 달성 페이스 (v0.3) — 시뮬레이터는 7단계
/finance/fixed           고정비 관리
/finance/categories      카테고리 · 그룹 관리 (v0.3)
/finance/settings        소득 설정 + 목표 + JSON 백업·복원
```

기존 라우트는 `/`, `/workouts/:id`, `/exercises`, `/templates`, `/templates/:id`, `/report`이며,
**`/report`(운동 주간 리포트)와 `/finance/report`는 다른 화면이다.** 이름이 겹치니 주의한다.

`App.tsx`의 캐치올 `<Route path="*" element={<Navigate to="/" replace />} />`가 마지막에 있으므로,
가계부 라우트는 그 **앞에** 추가해야 한다. 뒤에 두면 전부 홈으로 튕긴다.

**탭바는 영역에 따라 바뀐다.** 현재 하단 탭은 홈 / 종목 / 템플릿 3개다.
가계부에도 대시보드·입력·자산 등 여러 화면이 있어 한 탭바에 다 넣을 수 없다.

- `/finance/*` 에서는 가계부 탭바, 그 외에서는 기존 운동 탭바
- 서로 오가는 진입점: 운동 홈에 "가계부" 링크, 가계부 대시보드에 "운동 기록" 링크

#### 1.5.1 영역 전환 토글 (v0.5)

**운동 ↔ 가계부 전환은 좌측 상단 토글이다.** v0.4까지는 홈과 대시보드에 각각
링크를 두었는데, 화면 안 링크로 오가면 "지금 어느 쪽에 있는지"가 흐려진다.
두 영역은 데이터베이스부터 분리된 별개의 앱이므로 늘 같은 자리에서 현재
위치와 갈 수 있는 곳을 함께 보여준다.

**탭이 가리키는 최상위 화면에서만 띄운다.** 상세 화면은 좌측 상단이 뒤로가기
자리라 겹친다.

**탭은 4개로 묶는다 (v0.4)** — 대시보드 / 입력 / 자산 / 설정.
5개는 좁아 오조작이 늘고, 화면은 그보다 많다. 나머지는 링크로 들어간다.

| 화면 | 진입 경로 |
|---|---|
| 사이클 리포트 | 대시보드 → "사이클 리포트" |
| 목표 달성 페이스 | 대시보드 목표 카드, 설정 |
| 목표 시뮬레이터 | 목표 상세 하단, 설정 |
| 고정비 · 카테고리 관리 | 설정 |

운동 쪽 주간 리포트 진입점이 홈에 있는 것과 같은 방식이다(`spec-v0.3.md` §5).

### 1.6 기존 코드를 건드려도 되는 범위 (v0.2 추가)

§7이 "기존 운동 기록 기능 수정"을 금지하는데, 라우트를 추가하려면 `App.tsx`는 반드시 고쳐야 한다. 모순을 다음과 같이 푼다.

**허용**

- `App.tsx`에 가계부 라우트 추가, 탭바를 영역별로 분기
- 운동 홈에 가계부 진입점 링크 한 개 추가
- 기존 공용 컴포넌트를 **그대로 쓰는 것**

**금지**

- 기존 공용 컴포넌트의 시그니처·동작 변경 (`Button`에 variant 추가 포함)
- `src/db/`, `src/lib/`, `src/screens/` 안의 운동 로직 수정
- `workout-log` 스키마 변경

가계부에 필요한 UI 변형은 `src/finance/components/`에 새로 만든다. 중복이 생겨도 그쪽이 낫다 — 공용 컴포넌트를 고치면 운동 쪽 회귀를 검증할 방법이 없다.

## 2. 핵심 설계 원칙

### 2.1 급여 사이클

**월 단위 집계는 캘린더 월이 아니라 급여일 기준이다.**

- 기본 급여일: 매월 25일
- 한 사이클: `당월 25일 ~ 익월 24일`
- 예: "2026-10 사이클" = 2026-10-25 ~ 2026-11-24

```ts
/** date는 'YYYY-MM-DD' 문자열 — Transaction.date와 같은 형식이다 */
export function getCycleKey(date: string, payday: number): string
export function getCycleRange(cycleKey: string, payday: number): { start: string; end: string }
export function getCurrentCycleKey(payday: number): string
```

**v0.2 정정** — v0.1은 `getCycleKey(date: Date)`였으나 `Transaction.date`가 문자열이라 호출부마다 변환이 끼어든다. 입출력을 `'YYYY-MM-DD'` 문자열로 통일한다. `payday`를 인자로 받는 것은 아래 이유 때문이다.

**급여일은 상수가 아니라 설정값이다.** 하드코딩하면 급여일이 바뀔 때 저장된 모든 `cycleKey`가 틀어진다. 설정 변경 시 전체 `Transaction`의 `cycleKey`를 재계산하는 함수도 함께 만든다.

```ts
export async function recalculateAllCycleKeys(payday: number): Promise<number>
```

모든 집계는 반드시 이 유틸을 거친다. React에 의존하지 않으므로 `src/finance/lib/cycle.ts`에 순수 함수로 둔다(§0.2).

### 2.2 지출 / 저축 / 자산이전 구분

세 가지를 다르게 취급한다. 섞으면 저축률이 왜곡된다.

| 유형 | 의미 | 예시 |
|---|---|---|
| `EXPENSE` | 순수 소비 (돈이 사라짐) | 식비, 유류비, 관리비, 대출 **이자** |
| `SAVING` | 저축·투자 (자산으로 남음) | 적금 납입, 투자 매수 |
| `TRANSFER` | 부채 원금 상환 (순자산 증가) | 대출 원금, 할부 원금 |
| `INCOME` | 수입 | 급여, 기타 소득 |

**대출 상환은 원금(TRANSFER)과 이자(EXPENSE)를 분리 기록한다.**

#### 2.2.1 할부·대출은 원금과 이자를 나눈다 (v0.2 명시)

할부금을 통째로 고정비(EXPENSE)에 넣으면 위 원칙과 어긋난다.
`Debt`에 `monthlyPrincipal` / `monthlyInterest`가 따로 있으므로 이중 정의이기도 하다.

**원금은 `TRANSFER`, 이자는 `EXPENSE`로 각각 등록한다.** 잔액과 금리를 알면
월 이자를 계산해 나눌 수 있고, 고정비는 어차피 매 사이클 실제 금액으로 고치는
값이므로 근사로 시작해도 된다.

**분리하지 않으면** 저축률의 분자(TRANSFER)에서 원금 상환액이 통째로 빠져
실제보다 낮게 나온다.

### 2.3 저축률은 두 값을 병기한다

원안의 `(SAVING + TRANSFER) / 실수령액` 공식에는 분자·분모 불일치가 있다.
급여에서 **원천 차감**되는 부채 원금(회사 대출, 학자금 등)은 실수령액에 애초에
포함되지 않는다. 분자에만 있고 분모에는 없다.

원천 차감이 있으면 두 정의의 결과가 몇 %p씩 벌어지므로, 어느 하나를 고르지 말고
**둘 다 표시하고 라벨을 명확히 한다.**

```ts
// 실수령 기준 — "손에 쥔 돈 중 얼마를 남기는가"
const rateNet = (saving + transfer) / netPay

// 총소득 기준 — "버는 돈 전체 중 얼마를 남기는가"
const rateGross = (saving + transfer) / (netPay + withheldTransfer)
```

대시보드에는 실수령 기준을 크게, 총소득 기준을 작게 병기한다.

#### 2.3.1 `transfer`의 출처 (v0.2 명시 — 이중 계산 주의)

`transfer`는 두 곳에서 온다. **섞으면 이중 계산된다.**

| 출처 | 예 | 기록 방식 |
|---|---|---|
| **원천 차감** | 급여에서 바로 빠지는 부채 원금 | `IncomeSetting.deductions` 중 `isTransfer: true` 인 것의 합. **Transaction으로 만들지 않는다.** |
| **직접 이체** | 계좌에서 나가는 부채 원금 | `Transaction` (`type: 'TRANSFER'`) |

```ts
const withheldTransfer = deductions.filter(d => d.isTransfer).reduce((s, d) => s + d.amount, 0)
const paidTransfer = /* 이 사이클의 type === 'TRANSFER' 인 Transaction 합 */
const transfer = withheldTransfer + paidTransfer
```

원천 차감분을 `Transaction`으로도 자동 생성하면 저축률이 부풀려진다.
**급여에서 이미 빠져나간 돈은 `IncomeSetting`에서만 읽는다.**

### 2.4 금액과 날짜

- 금액은 **정수(원 단위)** 로만 다룬다. 부동소수 오차를 원천 차단한다.
- 날짜는 문자열 `YYYY-MM-DD`로 저장하고 표시 시점에 포맷팅한다.
- 타임스탬프가 필요한 필드(`updatedAt` 등)는 epoch ms(number)를 쓴다. 운동 쪽 규약과 동일(`spec-v0.3.md` §4.2).

### 2.5 삭제 정책 (v0.2 추가)

운동 쪽과 같다(`spec-v0.3.md` §5.3). **아카이브가 기본, 하드 삭제는 확인 다이얼로그 후.**

- `Category`를 하드 삭제하면 그 카테고리를 쓰던 `Transaction`이 고아가 된다. 삭제 전 사용 건수를 세어 확인문에 보여주고, 그래도 지우면 해당 거래를 "미분류" 카테고리로 옮긴다.
- `Transaction`은 아카이브 개념이 없다. 오입력은 바로 지운다.
- 순서 변경은 인접 항목 `sortOrder` 스왑. 운동 쪽 `swapSortOrder`와 같은 방식이되 `src/finance/db/`에 따로 둔다.

## 3. 데이터 모델

### 3.1 Dexie 스키마 (v0.2 추가)

v0.1에 인덱스 설계가 없었다. 집계 성능이 여기서 갈린다.

```ts
db.version(1).stores({
  transactions: 'id, date, cycleKey, categoryId, [cycleKey+type], [cycleKey+categoryId], [cycleKey+fixedCostId]',
  categories: 'id, sortOrder, type',
  fixedCosts: 'id, categoryId',
  assets: 'id, kind',
  debts: 'id',
  goals: 'id',
  netWorthSnapshots: 'cycleKey',
  incomeSettings: 'id',
})

// v0.3 — 그룹을 문자열에서 테이블로 승격
db.version(2)
  .stores({
    categories: 'id, sortOrder, type, groupId',
    groups: 'id, sortOrder',
  })
  .upgrade(/* 기존 group 문자열 → groups 생성 후 groupId 채움 */)
```

**그룹을 테이블로 올린 이유 (v0.3)** — `Category.group`이 자유 문자열이면 그룹
이름을 바꿀 때 카테고리를 전부 고쳐야 하고, 그룹 순서를 정할 수 없다. §1.2가
"빈 DB일 때 전부 선언"을 권했지만 이미 시드가 들어간 DB가 있을 수 있으므로
`version(2)` 마이그레이션으로 기존 문자열을 읽어 자동 변환한다.

- `[cycleKey+type]` — 대시보드의 사이클 지출·저축 합계
- `[cycleKey+categoryId]` — 사이클 리포트의 카테고리별 실적
- `[cycleKey+fixedCostId]` — §5.6의 고정비 중복 생성 방지
- `netWorthSnapshots`의 기본키는 `cycleKey`다. 사이클당 한 건이므로 자동 덮어쓰기가 된다.
- `incomeSettings`는 `id: 'default'` 단일 레코드다.

**인덱스에 없는 필드(`isArchived`, `isActive`, `isFixed`)는 메모리에서 거른다.** IndexedDB에서 boolean은 인덱스 키로 부적합하고, 카테고리 30여 개·고정비 20여 개 규모라 전체 스캔이 더 싸다. 운동 쪽과 같은 판단이다.

## 4. 초기 시드

**시드에 금액을 담지 않는다.** 소스에 실제 급여·자산·부채를 박아 두면 저장소를
공개하는 순간 그대로 노출된다. "데이터가 전부 로컬이라 저장소를 공개해도
무방하다"(§3.1)는 전제가 거기서 깨진다.

시드하는 것은 **분류 골격뿐**이다.

| 대상 | 시드 |
|---|---|
| 그룹 | 주거 · 통신 · 차량 · 식비 · 건강 · 생활 · 여가 · 저축·투자 · 부채 상환 · 수입 |
| 카테고리 | 위 그룹에 속한 일반적인 항목들. **예산은 전부 0** |
| 소득 설정 | 급여일 기본값만. 세전·실수령은 0, 공제는 항목명만(금액 0) |
| 고정비 | 만들지 않는다 — 금액이 있어야 의미가 있다 |
| 자산 · 부채 · 목표 | 만들지 않는다 |
| 거래 | 만들지 않는다 |

카테고리에는 §2.2의 네 유형이 모두 들어간다. 지출뿐 아니라 저축·투자(`SAVING`),
부채 원금 상환(`TRANSFER`), 수입(`INCOME`) 카테고리가 처음부터 있어야
저축률이 제대로 계산된다.

**DB가 비어 있을 때만 1회 넣는다.** `categories`가 0건이면 최초 실행으로 본다.
백업 복원 직후 다시 시드되면 데이터가 섞이므로 복원 경로에서는 호출하지 않는다.

금액·자산·부채·소득·목표는 사용자가 화면에서 직접 넣는다(§5.4, §5.7, §5.9).
모든 시드 항목은 이름·유형·그룹까지 수정하거나 지울 수 있다.

### 5.2 거래 입력 — `/finance/new`

**모바일에서 3탭 이내 완료가 최우선.** 실제 입력은 대부분 휴대폰에서 일어난다.

- 자주 쓰는 카테고리를 상단 퀵버튼으로 (사용 빈도순 자동 정렬)
- 금액 입력은 `inputMode="numeric"` + 천단위 콤마 자동 → 전용 `AmountField`(§0.3)
- 터치 타겟 최소 44px
- 저장 후 카테고리 선택은 남긴다 — 같은 항목을 연속으로 넣는 경우가 많다

#### 5.2.2 카테고리 선택 (v0.9 변경)

**그룹별 시트에서 고른다.** v0.8까지는 사용 빈도순 상위 12개를 칩으로 늘어놓았는데,
카테고리가 30개를 넘자 **한 번도 쓰지 않은 카테고리가 잘려 나가** 방금 만든 것이
목록에 없는 상태가 됐다.

- 선택된 카테고리를 필드처럼 크게 띄우고, 누르면 시트가 열린다
- 시트는 그룹 섹션으로 나뉘고 검색창이 있다 — 개수가 늘어도 찾는 경로가 일정하다
- 퀵버튼에는 **실제로 써 본 카테고리만** 올린다(최대 8개). 한 번도 안 쓴 것으로
  채우면 정작 자주 쓰는 것이 밀려난다

#### 5.2.1 주 단위 입력 (v0.3 추가)

**입력과 조회는 주 단위, 집계는 급여 사이클 단위다.** 예산·저축률은 사이클
기준(§2.1)을 그대로 두고, 거래를 넣고 확인하는 화면만 주차로 넘긴다.
둘을 합치면 예산 대비 집계가 깨진다.

- 주 시작은 월요일. 이전/다음 주로 이동한다.
- 두 달에 걸친 주는 **그 주의 목요일이 속한 달**로 센다(ISO 8601).
  8/31~9/6은 목요일이 9/3이므로 9월 1주차이고, 9/7~9/13이 9월 2주차다.
- 화면에는 "9월 2주차"와 "9/7 ~ 9/13"을 함께 띄운다.
- 그 주의 거래 목록과 지출 합계를 아래에 보여준다(오입력 즉시 확인용).
- 다른 주로 옮기면 입력 날짜 기본값도 그 주 안으로 맞춘다.

### 5.3 사이클 리포트 — `/finance/report`

- **최근 6사이클 지출·저축 추이 (라인, 최상단)** — v0.6.
  이번 사이클 숫자만으로는 늘었는지 줄었는지 알 수 없다.
- 카테고리별 예산 대비 실적 표 (예산 / 실제 / 차이)
- 전 사이클 대비 증감
- 고정비 vs 변동비 비중 (가로 막대)
- 지출 상위 5개 카테고리

**차이는 예산 − 실제다.** 음수면 초과이므로 빨강으로 표시한다.
예산도 지출도 0인 줄은 빼서 표를 짧게 유지한다.

### 5.4 자산 현황 — `/finance/assets`

- 자산 목록 + 총액 / 부채 목록 + 총액
- **순자산 = 자산 − 부채**
- 자산 종류별 비중 (도넛, Recharts) — 이 앱의 첫 Recharts 사용처다
- 월별 순자산 추이 (라인)
- **자산·부채 추가·수정·삭제** (v0.4)

부채는 **월 원금과 월 이자를 따로 입력받는다.** `monthlyPayment`는 둘의 합으로
자동 계산한다 — 따로 받으면 서로 어긋나고, 원금·이자 구분은 저축률의 근간이다(§2.2).

자산의 `updatedAt`은 저장할 때마다 갱신한다. 잔액을 언제 맞춰봤는지가 이 숫자의
신뢰도를 좌우한다.

#### 5.4.1 스냅샷 소급 정책 (v0.4 변경)

사이클이 끝나는 순간 앱이 켜져 있으리라는 보장이 없으므로 진입 시 소급한다.
기본키가 `cycleKey`라 중복 실행돼도 덮어쓸 뿐이다.

**직전 사이클 하나만 소급한다.** v0.3까지는 "마지막 스냅샷 이후 종료된 사이클"을
전부 채우게 되어 있었으나, 자산 테이블에는 **현재 잔액만 있고 과거 잔액은 어디에도
없다.** 빠진 사이클을 전부 채우면 값이 전부 같아져 그래프에 없던 이력을 지어내는
꼴이 된다. 하나만 찍고 다음 사이클부터 정확해지게 둔다.

추이 점이 2개 미만이면 차트 대신 "사이클이 끝날 때마다 한 점씩 쌓입니다"를 띄운다.

### 5.5 목표 시뮬레이터 — `/finance/goal`

**입력**
- 월 추가 저축액 (슬라이더)
- 예상 투자 수익률 (연 %, 기본 6%)
- 목표 시점 (기본 2029-03)

**출력**
- 목표 시점 예상 자기자금
- 대출 가능액
- 매수 가능 주택 가격

**정책 상수는 한 파일(`src/finance/lib/loanPolicy.ts`)에 모으고 기준일자를 명시한다.**

```ts
/**
 * ⚠️ 2026-08 시점의 입력값 기준. 검증되지 않은 값이다.
 * LTV·DSR·생애최초 요건은 정부 대책에 따라 수시로 바뀐다.
 * 실행이 가까워지면 주택도시기금 또는 은행 창구에서 반드시 재확인할 것.
 * 이 시뮬레이터는 방향 감각용이며 확정 계산기가 아니다.
 */
export const POLICY_AS_OF = '2026-08'

export const BOGEUMJARI = {
  maxLoan: 420_000_000,
  ltvCapital: 0.7,
  maxHousePrice: 600_000_000,
  incomeLimit: 70_000_000,
}

export const DIDIMDOL = {
  maxLoan: 240_000_000,
  ltvCapital: 0.7,
  incomeLimit: 85_000_000,
}
```

**계산**
```
실제 대출액   = min(한도, 주택가격 × LTV)
매수 가능가   = 자기자금이 (1 − LTV) 비율을 충당할 수 있는 최대 주택가격
부대비용      = 주택가격 × 약 2% (취득세·중개수수료·이사비) 별도 차감
```

**구간이 둘이라 식도 둘이다 (v0.4).** 대출이 한도에 닿기 전과 후의 식이 다르므로
둘 다 풀고 유효한 쪽을 고른다.

```
1) LTV 구간  : 자기자금 = P(1 − LTV + 부대비율)      → P = E / (1 − LTV + 0.02)
2) 한도 구간 : 자기자금 = P − 한도 + P × 부대비율     → P = (E + 한도) / 1.02
```

1번 결과의 대출액이 한도 안이면 그게 답이고, 넘으면 2번이 답이다.
마지막으로 `maxHousePrice` 상한을 적용한다. 상한에 걸리면 화면에
"자기자금을 더 모아도 이 상품으로는 더 못 올립니다"를 표시한다.

#### 5.5.1 자기자금 계산 (v0.5 수정 — 이전 버전은 틀렸다)

v0.4까지 `자기자금 = isLiquidByTarget이 true인 자산의 합`을 미래가치로 불린 값을
썼다. **세 군데가 틀렸다.**

| 오류 | 결과 |
|---|---|
| 부채를 빼지 않았다 | 보증금을 자산으로 세면서 대응하는 대출을 무시. 그만큼 통째로 부풀려진다 |
| 부채 상환분에도 복리를 먹였다 | 월 페이스 중 원금 상환분에는 이자가 붙지 않는다 |
| 투자가 아닌 자산에도 수익률을 적용했다 | 보증금·청약·현금에 투자 수익률이 붙었다 |

같은 데이터로 목표 상세(§5.8)는 "목표에 부족"이라 하고 시뮬레이터는 목표를
훌쩍 넘는 자기자금을 보여주면서 모순이 드러났다.

**고친 계산 (v0.6 — 월별 시뮬레이션)**

v0.5는 `− max(0, 총부채 − 월원금상환 × n)`으로 부채를 뭉뚱그렸다. 그러면
**전세대출처럼 월 원금 상환이 0인 부채까지 언젠가 갚는 것으로 계산된다.**
총부채를 총상환액으로 나누면, 이자만 내는 대출처럼 원금 상환이 0인 부채까지
언젠가 사라지는 것으로 계산된다.

한 달씩 굴린다. 공식보다 느리지만 부채가 **각자의 속도로** 사라지는 것을
정확히 반영하고, 시계열이 그대로 그래프가 된다.

```
매달:
  각 부채 d: 상환액 = min(d.balance, d.monthlyPrincipal); d.balance -= 상환액
  freed = 총 monthlyPrincipal − 이번 달 실제 상환액   ← 완납된 부채의 몫
  투자자산 ×= (1 + r/12)
  저축잔고 = 저축잔고 × (1 + r/12) + 월저축 + freed
  자기자금 = 투자자산 + 저축잔고 + 그 외 유동자산 − 남은 부채 합
```

- 수익률은 **`kind === 'INVESTMENT'`인 자산과 저축에만** 붙인다
- `isLiquidByTarget`이 false인 자산(연금)은 제외한다
- **완납된 부채의 상환액은 저축으로 전환된다고 본다.** 대출이 끝나면 그 돈이
  사라지는 게 아니라 여유가 된다. 실제로 저축으로 돌려야 이 계산이 맞으므로
  화면에 전제를 밝힌다.

**수익률 가정 하나로 결과가 몇 개월씩 갈린다.** 그래서 값을 고정하지 않고
직접 입력받는다(§5.5.3).

이러면 목표 상세의 순자산 기준과 일관된다 — **차이는 투자 수익분뿐이다.**
같은 데이터를 넣으면 두 화면의 차이는 투자 수익분에 그친다.

**내역을 화면에 펼친다.** 네 항목을 각각 보여주지 않으면 숫자가 맞는지 사용자가
확인할 방법이 없다. 이번 오류도 그래서 늦게 드러났다.

#### 5.5.3 예상 수익률은 직접 입력한다 (v0.7)

슬라이더(0~12%)를 숫자 입력으로 바꿨다. 몇 %를 가정할지는 사람마다 다르고,
범위를 미리 좁혀 두면 그 밖의 값을 넣을 수 없다.

- 기본 6%, **0~100%** 허용, 소수점 입력 가능
- 자르기는 **계산 시점에만** 한다. 입력 도중에 값이 튀면 못 고친다.
- 100%를 넘겨 입력하면 "최대 100%까지 반영됩니다"를 띄우되 입력 자체는 막지 않는다
- 목표 상세도 같은 입력을 쓴다. v0.6의 "0% / 6%" 토글은 그 두 값이 임의였다.

값 규칙(`clampRatePercent`)은 `lib/rate.ts`에, 입력 컴포넌트는
`components/RateField.tsx`에 둔다 — 상수와 컴포넌트를 한 파일에 두면
fast refresh가 깨진다(§0.2).

#### 5.5.2 그래프 (v0.6)

목표 상세와 시뮬레이터에 **자기자금 곡선 + 목표선**을 그린다.
"N개월 필요, 목표보다 M개월 늦음" 같은 숫자만으로는 얼마나 모자란지 감이
오지 않는다. 목표 금액(가로 점선)과 목표 시점(세로 점선)을 함께 그리면
곡선이 두 선의 교차점을 어디서 지나는지가 한눈에 보인다.

시뮬레이터에서는 수익률 슬라이더를 움직이면 곡선이 즉시 바뀌어,
수익률 가정이 결과를 얼마나 좌우하는지가 드러난다.

곡선은 목표 시점 이후까지 그린다 — 교차점이 화면 밖이면 판정이 보이지 않는다.

**DSR과 기존 부채 상환 부담은 계산에 넣지 않았다.** 실제 심사에서는 이쪽이 먼저
걸릴 수 있다. 화면 하단에 명시한다.

**화면 요구사항**
- `POLICY_AS_OF`를 화면에 표시한다. 코드 주석은 보지 않고 지나친다.
- 소득요건 초과 경고: 예상 연소득이 `incomeLimit`에 근접하면 경고 표시.
- "실제 대출 가능 여부는 금융기관 확인 필요" 문구를 결과 하단에 상시 노출.

### 5.6 고정비 관리 — `/finance/fixed`

- 고정비 목록 (활성/비활성 토글), **추가·수정·삭제** (v0.3)
- 삭제해도 이미 만들어진 거래는 남는다. 다음 사이클부터 자동 생성만 멈춘다.
- 종료 예정일 표시 및 **종료 임박 알림**
  예: "○○ 대출 2027-10 완납 예정 — 이후 그만큼 여력 증가"
- `startCycle` 이전, `endCycle` 이후 사이클에는 생성하지 않는다.

#### 5.6.1 거래는 자동으로 만들지 않는다 (v0.9 변경)

v0.8까지는 앱 진입 시 이번 사이클의 고정비 거래를 자동 생성했다. **없앴다.**

- 실제로 빠져나가지 않은 달에도 지출로 잡힌다
- 직접 입력한 건과 중복된다
- 금액이 달라진 달에는 틀린 값이 들어간다

대신 고정비 화면의 **[이번 사이클에 반영]** 버튼으로 사용자가 직접 만든다.
중복 방지는 그대로다 — 복합 인덱스 `[cycleKey+fixedCostId]`로 이미 만든 항목은
건너뛰므로 여러 번 눌러도 안전하다(§3.1).

### 5.7 설정 — `/finance/settings`

- 소득 설정 수정 (세전·실수령·급여일)
- **공제 내역 편집** (v0.3) — 항목 추가·삭제·이름·금액 수정, `isTransfer` 토글.
  세전 − 공제 ≠ 실수령이면 경고를 띄우되 저장은 막지 않는다.
- **목표 설정** (v0.3) — 이름·목표 시점(`YYYY-MM`)·금액·메모. 목표는 하나만 쓴다.
- 카테고리·그룹 관리(§5.9)와 목표 상세(§5.8)로 가는 링크
- **급여일 변경 시 전체 `cycleKey` 재계산**(§2.1). 영향 건수를 확인 다이얼로그에 표시한다.
- JSON 내보내기 / 가져오기 (§1.4)

### 5.8 목표 상세 — `/finance/goal` (v0.3 추가)

대시보드의 목표 카드를 누르면 들어온다. **지금 페이스가 목표에 닿는가**만 본다.

**시뮬레이터와 같은 월별 시뮬레이션을 쓴다 (v0.6).** v0.5까지는 여기만
`부족액 ÷ 월 페이스`로 단순 계산해서, 같은 데이터로 두 화면이 다른 개월 수를
말했다. 수익률을 0으로 본 것과 부채를 총액으로 뭉뚱그린 것이 원인이었다.

**수익률을 직접 입력받는다(§5.5.3).** 가정에 따라 결론이 크게 갈리므로
하나를 정해 보여주면 오해를 부른다.

- 판정을 맨 위에 크게: "지금 페이스면 도달합니다" / "지금 페이스로는 부족합니다"
- 현재 순자산, 목표까지 남은 금액, 남은 개월, 필요 월 적립, 현재 월 페이스,
  목표 시점 예상액, 지금 페이스로 달성하는 시점

**현재 월 페이스 = 저축·투자 예산 + 부채 원금 상환(원천 차감 포함).**
원금 상환도 순자산을 늘리므로 함께 센다(§2.2).

**목표 시점은 그 달의 말일 기준이다.** `"2029-03"`을 3월 1일로 잡으면 남은
기간이 한 달 짧아져 필요 적립액이 부풀려진다.

투자 수익률을 0으로 둔 단순 적립 계산이라 보수적이다. LTV·대출까지 넣은
시뮬레이터는 7단계(§5.5)이고, 이 화면은 그 전에 쓰는 방향 감각용이다.
현금화가 부분적인 자산이 있으면 결과를 낙관적으로 읽지 않도록 화면에 함께 알린다.

### 5.9 카테고리 · 그룹 관리 — `/finance/categories` (v0.3 추가)

- 그룹별 섹션으로 나뉘고, 각 섹션 아래에 그 그룹의 카테고리가 붙는다
- 카테고리: 추가·이름/유형/예산/그룹 변경·순서 이동·삭제
- 그룹: 추가·이름 변경·순서 이동·삭제
- **카테고리가 남아 있는 그룹은 삭제를 거부한다.** 그룹만 지우면 안의
  카테고리가 갈 곳을 잃는다.
- 카테고리 하드 삭제 시 그 카테고리를 쓰던 거래는 '미분류'로 옮기고,
  연결된 고정비는 함께 지운다(§2.5).

## 6. 구현 순서

각 단계마다 동작 확인 후 다음으로 넘어간다. 한 번에 전부 구현하지 않는다.
운동 쪽 CLAUDE.md의 "한 번에 한 화면씩" 규약과 같다.

```
0  라우팅 셸 — /finance 라우트, 영역별 탭바, 양방향 진입점   ✓ 완료
1  급여 사이클 유틸 + 타입 정의 + Dexie 저장소 레이어        ✓ 완료
2  카테고리 / 고정비 시드 + 관리 화면 + JSON 백업·복원       ✓ 완료
3  거래 입력 화면 (주 단위, 모바일 최적화)                   ✓ 완료
4  대시보드 (전 사이클 대비 포함)                            ✓ 완료
   + 목표 설정·달성 페이스 화면                              ✓ 완료 (v0.3 추가)
5  사이클 리포트                                             ✓ 완료
6  자산 / 부채 관리 + 순자산 스냅샷                          ✓ 완료
7  목표 시뮬레이터 (LTV·수익률)                              ✓ 완료
```

**전 단계 구현이 끝났다.** 남은 것은 실사용 검증이다 — 시뮬레이터는 스펙이
경고한 대로 "실제 데이터가 쌓인 뒤라야 검증된다."

**실기기 확인이 필요하다.** 개발 환경에 브라우저가 연결되어 있지 않아 화면을
눈으로 확인하지 못했다. 특히 Recharts 차트의 좁은 화면 렌더링, `<input type="date">`와
`type="range"`의 iOS 동작, 백업 파일 다운로드(`<a download>`는 iOS 스탠드얼론
PWA에서 동작이 다르다)가 그렇다.

0단계를 앞에 둔 이유는 화면 하나를 붙일 때마다 라우트를 손대면 §1.6의 "허용 범위"를 반복해서 건드리게 되기 때문이다. 셸을 먼저 세우고 그 안을 채운다.

**단계마다 `npx tsc --noEmit`과 `npm run lint`를 통과시킨다.** 계산 로직(사이클 유틸, 저축률, 대출)은 React에 의존하지 않으므로 Node에서 직접 돌려 검증할 수 있다(§0.2).

## 8. 열어둔 문제

| 항목 | 내용 |
|---|---|
| `isLiquidByTarget`이 boolean | 목표 시점에 일부만 회수되는 자산(보증금 등)을 표현하지 못한다. 비율 필드가 필요해지면 다음 버전에서 다룬다. |
| 할부 이자는 근사 | §2.2.1의 원금·이자 분리는 잔액 기준 추정이라 실제 상환 스케줄과 다를 수 있다. |
| 운동 쪽 백업 미구현 | §1.4. 이 형식이 먼저 확정되고 운동 쪽이 따라온다. |
| 사이클 경계의 거래 | 급여일 변경 시 이미 지난 사이클의 `cycleKey`도 바뀐다. 과거 리포트가 소급 변형되는 것이 맞는지 실사용 후 판단한다. |
| 과거 순자산 이력 없음 | 자산에 현재 잔액만 있어 스냅샷을 소급할 수 없다(§5.4.1). 추이 그래프는 지금부터 쌓인다. |
| DSR 미반영 | 시뮬레이터가 LTV·한도·소득요건만 본다. 실제 심사는 DSR이 먼저 걸릴 수 있다. |
| 자산 잔액은 수동 갱신 | 계좌 연동이 범위 밖(§1.3)이라 직접 고쳐야 한다. `updatedAt`으로 마지막 갱신 시점만 남긴다. |
| 보증금과 대응 대출의 연동 | 보증금을 회수하면 그에 걸린 대출도 함께 사라지는데, 지금은 둘을 각각 자산·부채로 계산할 뿐 연동하지 않는다. 순자산 기준이라 합계는 맞지만 회수 시점의 현금 흐름은 표현하지 못한다. |
| 전 사이클 대비의 기준 | 사이클 전체끼리 비교한다. 사이클 중반이면 이번 달이 당연히 적게 나온다. 같은 경과일 기준 비교가 필요한지 실사용 후 판단한다. |
